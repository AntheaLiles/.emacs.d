# Emacs runtime performance dataset

## Scope

This collector is intentionally package-agnostic and major-mode-agnostic. It observes Emacs runtime behavior using built-in facilities only. Package or mode names may appear in observations, but are never encoded as collection logic.

The dataset is intended for longitudinal, post-hoc analysis by an external analyst or LLM.

## Runtime model

One `run_id` corresponds to one Emacs process lifetime.

The collector is installed from `early-init.el`, but telemetry starts from `emacs-startup-hook`. This deliberately excludes the normal startup phase from the long-running usage measurements. A daemon therefore remains compatible with the same model: the runtime is the daemon process lifetime rather than an individual client lifetime.

`run_id` identifies the Emacs process lifetime. Every longitudinal row carries it. `seq` is a monotone observation sequence generated by the collector and is unique to an observation within a run; derived rows such as CPU-summary rows may share the same `seq` as their source observation. It is not a causal ordering across Emacs internals.

`timestamp` is wall-clock time and is intended for temporal correlation across files.

## events.tsv

Contains only interactive commands whose wall-clock duration is at least `command_threshold_ms`.

`command_wall_ms` is elapsed wall-clock time between the command hooks. It is a latency indicator, not a CPU measurement and not a guarantee of total display latency.

`emacs_cpu_ms` is CPU time consumed by the Emacs process during the same interval. It comes from `current-cpu-time` and is independent of wall-clock elapsed time.

`gc_count_delta` and `gc_time_delta_ms` indicate GC activity observed between the two command hook measurements.

A large wall time with small Emacs CPU time indicates that the delay is not primarily CPU consumption by the Emacs process.

## gc.tsv

One row is emitted after each observed GC through `post-gc-hook`.

`gcs_done` and `gc_elapsed_total_s` are cumulative Emacs counters. The collector also computes `gc_time_delta_ms` and `gc_count_delta` against the previous GC observation. `gcs_done` and `gc_elapsed_total_s` remain cumulative, preserving the raw counters.

No advice or wrapper is installed around `garbage-collect`.

## alloc.tsv

Periodic cumulative allocation counters returned by `memory-use-counts`.

They measure allocation activity over the Emacs session, not live memory. Differences between successive observations give allocation rates.

## processes.tsv

Periodic snapshots of the Emacs process and local OS processes that are descendants of the Emacs PID according to their parent-PID chain.

`source=emacs+system` means Emacs also exposes the PID as an Emacs process object. `source=system` means it is visible at the system-process level but not as an Emacs process object. System-process queries are explicitly local to the Emacs host.

`utime_s` and `stime_s` are cumulative process CPU times. Differences between snapshots are more useful for interval CPU analysis than the lifetime `pcpu` value.

This does not provide CPU accounting for remote processes (for example a language server running on another host). Network or remote work may instead appear as wall-clock latency with little local CPU usage.

Processes that daemonize and cease to be descendants of Emacs can also escape this local descendant scan.

## system.tsv

Periodic environmental observations: system load averages and available system memory when supported.

These values are confounders, not evidence that a specific Emacs component is responsible for a delay.

## cpu/index.tsv

One row per native CPU profiler segment.

The built-in profiler samples Emacs call stacks using the native CPU profiler. In Emacs 31.1, `profiler-cpu-log` extracts the current log and creates a fresh log for future samples while the profiler remains active. Therefore segment rotation does not require `profiler-reset` or a profiler restart.

`sample_count` includes recorded special entries. `discarded_samples` reports profiler-log overflow. A high discarded count means that absence of a stack from the profile cannot safely be interpreted as absence of execution.

`automatic_gc_samples` counts samples classified by the native profiler as Automatic GC.

## cpu/summary.tsv

Compact top-call-stack summaries generated from each native CPU profile. This file exists even when raw `.elprof` retention is disabled.

The stack is represented from outer to inner call, separated by ` > `. This is a compact approximation of the native profiler call stacks; raw `.elprof` files remain the authoritative profile representation when retained.

## cpu/*.elprof

Native Emacs profiler profile files. They can be opened with `profiler-find-profile`.

Retention is controlled by `my/perf-keep-cpu-profiles`. For a month-long campaign, retaining raw profiles can produce substantial storage usage; `cpu/summary.tsv` is the compact analysis layer.

## Data-integrity safety

Telemetry writes are performed from dedicated hidden buffers. The flush operation
must explicitly make the telemetry buffer current before reading or erasing it.
No operation in the collector is allowed to use `point-min`, `point-max`, or
`erase-buffer` on the caller's current user buffer. This is a hard data-integrity
invariant.

The collector also binds `default-directory` to `user-emacs-directory` when
querying local system memory and OS processes. This prevents the result from
becoming dependent on the current buffer's directory or a TRAMP remote host.

## overhead.tsv

This file is essential for interpreting the dataset. It measures the collector's own wall-clock and Emacs CPU cost for periodic operations such as process snapshots, allocation snapshots, CPU-profile rotation, and flushing.

The profiler CPU traces can also contain functions in the `my/perf--...` namespace and built-in `profiler-*` functions invoked by this collector. These are observer overhead, not configuration bottlenecks, and should be discounted or analyzed separately.

The collector does not attempt to hide its own activity from the profiler. Hiding it would make measurement validity harder to assess.

Process command-line arguments are disabled by default because command lines may contain sensitive data. Enable `my/perf-log-process-args` only deliberately.

## Recommended interpretation order

1. Detect anomalous command latencies in `events.tsv`.
2. Compare wall-clock and Emacs CPU time.
3. Correlate the event timestamp with the enclosing CPU segment.
4. Inspect GC and allocation observations around the same interval.
5. Inspect local child-process CPU deltas and system load.
6. Treat CPU-stack absence as non-proof when `discarded_samples` is non-zero.
7. Distinguish observed temporal correlation from causal attribution.

No field in this dataset establishes causality by itself.
